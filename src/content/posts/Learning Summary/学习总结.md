## 有关于go

### go的设计哲学：“少即是多”

####  语法简洁

Go 语言简单易学，学习曲线平缓，不需要像 C/C++ 语言动辄需要两到三年的学习期。Go 语言被称为“互联网时代的C语言”。Go 语言的风格类似于C语言。其语法在C语言的基础上进行了大幅的简化，去掉了不需要的表达式括号，循环也只有 for 一种表示方法，就可以实现数值、键值等各种遍历。

Go 语言提供了一套格式化工具——go fmt。一些 Go 语言的开发环境或者编辑器在保存时，都会使用格式化工具进行修改代码的格式化，这样就保证了不同开发者提交的代码都是统一的格式。(吐槽下：再也不用担心那些看不懂的黑魔法了…)

#### 并发介绍

- 进程和线程

```
    A. 进程是程序在操作系统中的一次执行过程，系统进行资源分配和调度的一个独立单位。
    B. 线程是进程的一个执行实体,是CPU调度和分派的基本单位,它是比进程更小的能独立运行的基本单位。
    C.一个进程可以创建和撤销多个线程;同一个进程中的多个线程之间可以并发执行。
```

- 并发和并行

```
    A. 多线程程序在一个核的cpu上运行，就是并发。
    B. 多线程程序在多个核的cpu上运行，就是并行。
```

- 协程和线程

```
协程：独立的栈空间，共享堆空间，调度由用户自己控制，本质上有点类似于用户级线程，这些用户级线程的调度也是自己实现的。

```

- goroutine 只是由官方实现的超级"线程池"。

每个实力`4~5KB`的栈内存占用和由于实现机制而大幅减少的创建和销毁开销是go高并发的根本原因。

- 并发不是并行：

并发主要由切换时间片来实现"同时"运行，并行则是直接利用多核实现多线程的运行，go可以设置使用核数，以发挥多核计算机的能力。

- goroutine 奉行通过通信来共享内存，而不是共享内存来通信。

说到go就不得不谈论其通过 **goroutine** 和 **channel** 实现了“不要通过共享内存来通信，而应该通过通信来共享内存”的哲学。

- 在现代操作系统中，分配资源的基本单位是**进程**。而在进程中，独立运行和调度的基本单位是**线程**。但是，在Go语言中，执行和调度的基本单位是**协程**。为了更高效的执行协程，Go语言实现了自己的**协程调度模型**。

  我们通过下面的一段简单代码来帮助你更好的理解Go程序中的协程。

  ```javascript
  for i := 0; i < 4; i++ {
          go func() {
                  time.Sleep(time.Second)
          }()
  }
  fmt.Println(runtime.NumGoroutine())
  ```

  上述代码最终输出结果是 5。也就是说在这段代码中启动了5个协程。但这里的问题是，这5个协程并不能直接向操作系统申请运行资源（CPU、内存等），而是必须要被分配给**内核态下的线程**才能执行，也就是说要依赖于操作系统级别的**线程调度模型**才行。根据用户级线程和内核级线程之间的对应关系，有三种模型：**1对1**、**N对1**和**M对N**。以上5个goroutine是如何分布在内核级线程上的？这是由Go的goroutine调度程序决定的。

  ![img](https://developer.qcloudimg.com/http-save/yehe-4464565/e8ed34cc63fe54c7cab4caec3d12f232.png)

  **GMP模型**

  在Go语言中，协程调度器是基于G-M-P模型实现的。

  - G：代表协程
  - M：操作系统下内核态的线程。在Go中能支持的最大线程数量是10000个，但一般情况下不会创建这么多线程。
  - P：处理器，可以把它理解为这时候一个等待被分配给M的协程队列。P的数量一般通过参数`runtime.GOMAXPROCS`设定。

  下面是一个1个M只绑定1个P的关系模型。如下图：

  ![img](https://developer.qcloudimg.com/http-save/yehe-4464565/3bb8438be10ae3d9c49182392029ace5.png)

  **协程被执行的流程（goroutine tour）**

  在代码中，当通过代码` go func(){}`启动一个协程后，GMP是如何工作的呢？下图详细解释了GMP是如何调度协程的。

  ![img](https://developer.qcloudimg.com/http-save/yehe-4464565/761e5f24a0005525e87b2b24a2ed16fd.png)

  1. 首先是创建新的协程
  2. 如果在本地的队列中有足够的空间，则会直接进入本地队列等待M的执行；如果本地队列已经满了，则进入全局队列（在GMP模型中，所有的M都可以从全局队列中获取协程并执行）
  3. 协程必须在M上才能执行，M和P是一对一的绑定关系，如果在M绑定的P中存在可以执行的G，则从P中拉出G来执行；如果P为空并且不存在可执行的G，则M从全局队列中取出G；如果全局队列也是空的，则从另一个P中提取G。
  4. 为G的运行分配必要的资源，并等待CPU对其进行调度。
  5. 分配CPU资源，并执行 `func(){} `函数。

  **调度策略**

  对于goroutine调度器来说最重要的调度策略是：**重用，避免频繁的资源创建和破坏，最大限度地提高系统吞吐量和并发性**。这是操作系统进行线程调度的最终目标。重用也是许多“池技术”的基础。围绕这一原则，goroutine调度器通过以下方式优化调度策略：

  1. 工作队列窃取机制：当线程 M 空闲时，会从其他的繁忙的队列P中”窃取“任务G来执行，而不是销毁空闲的线程 M。因为线程的创建和销毁都会消耗系统资源，避免频繁的创建线程和销毁线程可以打打提高系统的并发性。
  2. 切换机制：当一个线程M被阻塞时，M会主动将P切换到另一个空闲的M。

  此外，在go的1.14版本中，go语言技术团队试图向调度器中添加可抢占技术，具体可参考：https://github.com/golang/go/issues/24543

  - **总结**：一个线程M对应一个调度器P，一个调度器中有多个协程G，那么cup分配线程M的执行时间就可以再进

    步的分配给的其绑定的调度器P中所有的协程G，同一时间一个调度器中线程M执行一个协程G
    
    （补：P与M一般也是一一对应的。他们关系是： P管理着一组G挂载在M上运行。当一个G长久阻塞在一个M上时，runtime会新建一个M，阻塞G所在的P会把其他的G 挂载在新建的M上。当旧的G阻塞完成或者认为其已经死掉时 回收旧的M。）

### Go的另一设计哲学：通信共享内存

#### **不要通过共享内存来通信，而应该通过通信来共享内存。**

虽然可以使用共享内存进行数据交换，但是共享内存在不同的goroutine中容易发生竞态问题。为了保证数据交换的正确性，必须使用互斥量对内存进行加锁，这种做法势必造成性能问题。

Go语言的并发模型是CSP（Communicating Sequential Processes），提倡通过通信共享内存而不是通过共享内存而实现通信。

如果说goroutine是Go程序并发的执行体，channel就是它们之间的连接。channel是可以让一个goroutine发送特定值到另一个goroutine的通信机制。

Go 语言中的通道（channel）是一种特殊的类型。通道像一个传送带或者队列，总是遵循先入先出（First In First Out）的规则，保证收发数据的顺序。每一个通道都是一个具体类型的导管，也就是声明channel的时候需要为其指定元素类型。

**例如**： *共享内存方式：用锁保护全局变量*

多个 goroutine 直接操作同一个变量 `counter`，通过 `sync.Mutex` 保证互斥访问。

```go
package main

import (
    "fmt"
    "sync"
)

var (
    counter int
    mu      sync.Mutex
)

func increment(wg *sync.WaitGroup) {
    defer wg.Done()
    mu.Lock()        // 获取锁，进入临界区
    counter++        // 修改共享内存
    mu.Unlock()      // 释放锁，离开临界区
}

func main() {
    var wg sync.WaitGroup
    totalGoroutines := 1000

    for i := 0; i < totalGoroutines; i++ {
        wg.Add(1)
        go increment(&wg)
    }

    wg.Wait()
    fmt.Println("Final counter (shared memory):", counter)
}
```

**要点解释：**

- `counter` 是一个全局变量，所有 goroutine 都能直接访问（共享内存）。

- `mu.Lock()` 和 `mu.Unlock()` 形成一个**临界区**，确保同一时间只有一个 goroutine 能修改 `counter`，防止数据竞争。

- 数据交换的体现：每个 goroutine 通过“递增”这个动作向 `counter` 写入结果，主 goroutine 最后通过读取 `counter` 获取最终值。

  

*通信共享内存方式：用 channel 传递数据和所有权*

我们不共享 `counter` 变量本身，而是用一个 goroutine 作为**唯一的“计数器守护者”**，所有递增请求通过 channel 发送给它，它负责修改计数并返回结果。

go

```go
package main

import (
    "fmt"
)

func counterManager(incCh chan struct{}, resultCh chan int) {
    counter := 0
    for range incCh {
        counter++
    }
    resultCh <- counter
}

func main() {
    incCh := make(chan struct{})    // 用来发递增请求
    resultCh := make(chan int)      // 用来回传最终结果

    // 启动唯一的计数器管理器 goroutine
    go counterManager(incCh, resultCh)

    totalGoroutines := 1000
    var wg sync.WaitGroup // 这里仅用于等待所有请求发送完成

    // 启动 1000 个 goroutine，它们不直接读写 counter，而是发送请求
    for i := 0; i < totalGoroutines; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            incCh <- struct{}{} // 通过 channel 发送“递增”请求
        }()
    }

    // 等所有请求都发送完毕，然后关闭递增请求 channel
    wg.Wait()
    close(incCh)

    // 从结果 channel 读取最终计数器值
    finalCounter := <-resultCh
    fmt.Println("Final counter (channel way):", finalCounter)
}
```

**要点解释：**

- 全局变量 `counter` 被“隐藏”在 `counterManager` goroutine 内部，外部 goroutine 无法直接接触。
- 外部 goroutine 通过向 `incCh` 发送一个空结构体，表达“请帮我递增计数器”的意图，**数据（递增请求）通过 channel 传递**。
- 真正的计数器变量 `counter` 只被 `counterManager` 这一个 goroutine 拥有和修改，从设计上避免了数据竞争，**无需显式锁**。
- 最终结果也是通过 `resultCh` 传递出来，而不是读取共享变量。这体现了“通过通信来共享内存”。

##### 但并非说就一定要去使用channel

Channel 虽然是语言内置的，但它背后有复杂的实现：发送和接收可能涉及 goroutine 的**阻塞、唤醒、调度**，以及内部缓冲区的**内存分配、锁竞争**。这种成本在面对**高频、简单的共享状态**时，会显得过高。

**对比：一个计数器场景**

- **用 `sync.Mutex`**：几个 CPU 指令的锁操作，临界区极短。
- **用 `sync/atomic`**：单条原子指令，无阻塞，性能最优。
- **用 channel**：每次递增都要发送一个消息到 channel，管理器 goroutine 再接收处理，最后还要发回结果。这涉及多次上下文切换和内存同步。

在需要对一个变量进行**百万级、千万级并发写入**时，锁（尤其是原子操作）的性能优势是碾压级的。很多项目中的连接池计数、请求统计、降级开关等，直接用原子变量或 Mutex 是更高效的选择。

###### 补：有关于读写锁：

互斥锁是完全互斥的，但是有很多实际的场景下是读多写少的，当我们并发的去读取一个资源不涉及资源修改的时候是没有必要加锁的，这种场景下使用读写锁是更好的一种选择。读写锁在Go语言中使用sync包中的RWMutex类型。

读写锁分为两种：读锁和写锁。当一个goroutine获取读锁之后，其他的goroutine如果是获取读锁会继续获得锁，如果是获取写锁就会等待；当一个goroutine获取写锁之后，其他的goroutine无论是获取读锁还是写锁都会等待。

*如果仅用写锁不用读锁会出现脏读的情况*

## 关于数据库

### 关系型数据库

关系型数据库擅长处理结构化、高一致性要求的数据，并支持复杂查询、高度约束与关联关系，是大多数企业应 用的主流选择。例如订单管理、库存查询、用户注册登录、商品信息管理等，都普遍采用关系型数据库实现。

#### 目前常用的数据库

Mysql和Postgresql，这两个数据是我目前最常使用的，个人觉得mysql上手更加简单（虽然都是用的gorm🤣），尽管mysql其在高并发下有更好的性能，并且能胜任绝大部分场景，我还是更倾向于使用postgresql，**“**PostgreSQL 是“可编程数据库”，你可以把整个系统当作一个“应用平台”来扩展；而 MySQL 更像是一个“执行引擎”。网上有很多好用的扩展功能的插件供pgsql使用，如apache的[age](https://github.com/apache/age)。

#### 一些使用数据库时需要注意的地方

- **索引**：

  1. 什么是索引：

  - 索引是存储引擎用于**快速找到数据的一种数据结构**。在MySQL中，索引是在存储引擎层实现的，而不是服务器层。
  
  
  
  2. 索引的好处
  
  - 大大减少存储引擎需要扫描的数据量
  - 排序以避免使用临时表
  - 把随机I/O变为顺序I/O
  
  3. 索引的底层
  
  - 使用b+树作为索引结构
  
  - **B+树**
  
    - b+树结构简图
  
    假设我们有一组数据：3, 7, 10, 15, 20, 25, 30, 35
  
    ```
                         [非叶子节点：只存路标]
                               [20]
                             /      \
                            /        \
                           /          \
              [10]--------------------[30]
             /     \                 /     \
            /       \               /       \
    [3, 7, 10]  [15, 20]       [25, 30]  [35, 40]
       ↑  ↑       ↑  ↑           ↑  ↑       ↑  ↑
       |  |       |  |           |  |       |  |
      叶子节点   叶子节点       叶子节点   叶子节点
     (存真实数据)(存真实数据)  (存真实数据)(存真实数据)
       ⇄  ⇄       ⇄  ⇄           ⇄  ⇄       ⇄  ⇄  <-- 双向链表连接
    ```
  
    - 关于**根节点**的选取：**B+树在插入数据时，会自动进行“分裂”，中间值会被顶上去当“路标”。**
  
    B+树不是一开始就长好架构的，它是随着数据一条条插入，**自下而上**生长出来的。
  
    - 关于**非叶子节点**的选取：非叶子节点里的值，是**严格按照从小到大（升序）从左到右排列的**
  
    - **b+树永远有序**：不管你的输入多随机，底层都会排好序。这就是为什么随机主键/索引会导致性能问题的原因——*因为要时刻在中间插队，导致节点频繁分裂移动（页分裂），而自增主键只需要在末尾追加。*
  
    - 关于**二级索引**：用来储存**索引列的值**和对应的**主键值**
  
      - 二级索引的结构简图
  
      假设我们有一张用户表 `user`：
  
      `id`：主键（自增）
  
      `account`：账号（随机生成，建有普通索引）
  
      `name`：姓名（无索引）
  
      表里有如下4条数据：
  
      | id (主键) | account (账号) | name (姓名) |
      | :-------- | :------------- | :---------- |
      | 10        | DDD            | 赵六        |
      | 20        | BBB            | 李四        |
      | 30        | AAA            | 张三        |
      | 40        | CCC            | 王五        |
  
      此时，InnoDB 在磁盘上会为你维护**两棵 B+树**：
  
      ####  主键索引树（聚簇索引）：存完整数据
  
      数据按 `id` 排序，叶子节点存整行。
  
      ```
      【主键索引树】 (叶子节点存完整数据)
      
                       [20]
                     /      \
                   /          \
                [10]          [30]          ---> 非叶子节点(只存id路标)
               /    \        /    \
        [10, DDD, 赵六]  [20, BBB, 李四]  [30, AAA, 张三]  [40, CCC, 王五] ---> 叶子节点(整行数据)
      ```
  
      ####  account 二级索引树：只存 account 和 id
  
      数据按 `account` 字母顺序排序，叶子节点**只存 account 和 id**。
  
      ```
      【account 二级索引树】 (叶子节点不存完整数据，只存id作为"书签")
      
                       [CCC]
                     /      \
                   /          \
                [BBB]         [DDD]         ---> 非叶子节点(只存account路标)
               /    \        /    \
         [AAA, 30]  [BBB, 20]  [CCC, 40]  [DDD, 10] ---> 叶子节点(account + id)
           ⇄         ⇄          ⇄          ⇄      <-- 双向链表
      ```
  
      *注意看叶子节点：`[AAA, 30]` 表示账号是 AAA，它对应的主键 id 是 30。*
  
    - 关于`字符串`和`字符`的索引排序：*字符*按照字母表abc的顺序，*字符串*按照首字母进行字母表排序*（如果前面的字相同，按短的排前面（包括字符串）比如李<李四，第一个字相同比下一个字，拼音首字母相同比较下一个字母，同音不同字的拼笔画）*
  
- **事务**：

  事务（Transaction）是数据库中最重要的机制之一，用于确保数据操作的可靠性。保证多条操作作为一个整体， 要么全部成功，要么全部失败，只要业务中包含“多个步骤一起完成”，就必须使用事务。 

  - *事务遵循 ACID 原则*：

     A：**原子性（Atomicity）** 多条操作要么全部成功，要么全部失败，不存在部分成功。 

    C：**一致性（Consistency） **数据必须从一个合法状态转移到另一个合法状态，不能出现破坏规则的情况。 

    I：**隔离性（Isolation） **多个事务同时运行时不能互相干扰。 

    D：**持久性（Durability） **事务提交之后数据必须持久存储，不会丢失。 

    在实际业务中，事务常见于： 扣库存并创建订单 用户转账 修改多个表时需要保持同步 删除用户时需要清理关联数据 事务保证复杂操作的可靠执行，是企业级系统的基础保障

  - *四种隔离级别与现象*：

    **脏读（Dirty Read）  **：读到了别人 未提交 的数据。 脏读违反了事务隔离性原则，是最不安全的一种读取行为。 例子： 事务 A 把成绩改成 100（没提交） 事务 B 查询看到是 100 事务 A 回滚 → B 读到了一个“从未真正存在的数据” 

    **不可重复读（Non-repeatable Read）  **：同一事务内两次查询同一行结果不一样。 这就导致同一事务内，两次查询结果不稳定。 例子： A 第一次查询成绩为 90 B 修改成绩为 80 并提交 A 再查变成 80 → 行记录内容发生变化 

    **幻读（Phantom Read）  **同一事务内，两次查询发现多出（或少了）记录。 例子： A 查询某班有 30 人 B 插入一个学生 A 再查变成 31 人 → 查询结果的“行数量”变化了

  - `Gorm Hook`
  
    1. **hook是什么**：
  
    hook是gorm提供的回调机制，允许开发者在模型操作的生命周期中嵌入自定义逻辑。***通过hook，可以在数据库操作前后执行待定的代码***
  
    2. **hook实现**：
  
       假设我们有User表，对应model如下，则可以定义BeforeCreate hook，用于插入数据前的检查。
    
       ```go
       type User struct {
           ID int64
           Name string
           Age int32
           IsAdmin bool
           IsValid bool
           LoginTime time.Time
       }
       func (u *User) BeforeCreate(tx *gorm.DB) (err error) {
           if u.Age < 10 || u.Name == ""{
               return errors.New("invalid Age or Name")
           }
           return nil
       }
       ```
    
       
    
    3. **GORM 有哪些 Hook**
    
       GORM 针对主要的数据库操作（增、删、改、查），都提供了“之前”和“之后”的 Hook：
  
       - 创建
         - `BeforeCreate`：创建之前（比如：加密密码、生成UUID）
         - `AfterCreate`：创建之后（比如：发送欢迎邮件、写日志）
       - 更新
         - `BeforeUpdate`：更新之前（比如：记录是谁在修改）
         - `AfterUpdate`：更新之后
       - 删除
         - `BeforeDelete`：删除之前（比如：检查是否有关联数据，阻止违规删除）
         - `AfterDelete`：删除之后（比如：清理缓存）
       - 查询
         - `AfterFind`：查询之后（比如：把查出来的日期格式化成想要的字符串）
    
       *(注意：查询没有 BeforeFind，因为查之前你通常不需要改什么)*
    
  - `Gorm Session`
  
    1. **session是什么**：
  
    GORM Session是一种轻量级的数据库会话管理机制，它允许你在不创建新数据库连接的情况下，为不同的操作设置独立的配置环境。
  
    2. **session的应用**
  
       - 场景 1：临时跳过 Hook（上一节提到的）
  
       你有一个特殊的批量导入任务，不想触发 `BeforeCreate` 的加密 Hook，但其他的创建请求依然需要 Hook。
  
       ```
       // 全局 db 依然是干净的
       // 使用 Session 创建一个临时的分身，并设置 SkipHooks: true
       dryDB := db.Session(&gorm.Session{SkipHooks: true})
       
       // 用分身去创建，不会触发 Hook
       dryDB.Create(&User{Username: "批量导入用户1", Password: "123456"})
       
       // 用全局 db 去创建，依然会正常触发 Hook，密码会被加密
       db.Create(&User{Username: "正常注册用户", Password: "123456"})
       ```
  
       - 场景 2：DryRun（演练模式 / 只看不摸）
  
       有时候你只是想看看 GORM 生成的 SQL 语句对不对，但**不想真的把数据写进数据库**。这就像军事演习，只开枪不放弹。
  
       ```
       // 开启 DryRun 模式
       testDB := db.Session(&gorm.Session{DryRun: true})
       
       var user User
       // 这行代码会在后台打印出 SQL，但数据库里绝对不会多出这条记录
       testDB.Where("name = ?", "张三").First(&user) 
       ```
  
       *注：DryRun 常配合 `db.Debug()` 或者日志系统一起使用，用来调试复杂的 SQL。*
  
       - 场景 3：NewDB（清除之前链式调用的残骸）
  
       GORM 有一个很方便的“链式调用”特性：
  
       ```
       db.Where("age > 18").Where("city = ?", "北京").Find(&users)
       ```
  
       但是，如果你不小心把 `db.Where` 存到了一个变量里，就会出大问题：
  
       ```
       // 请求 1：
       adultDB := db.Where("age > 18") 
       adultDB.Find(&users) // 查出大于18岁的
       
       // 请求 2（同一个并发环境）：
       adultDB.Where("city = ?", "上海").Find(&users) 
       // ❌ 糟糕！这时候查出的不仅是上海的人，还带着上次 "age > 18" 的条件！
       ```
  
       为了安全地复用部分条件，你可以用 `NewDB: true` 来切断之前的条件：
  
       ```
       // 基础条件
       adultDB := db.Where("age > 18")
       
       // 克隆一个全新的分身，它带着 "age > 18"，但不会累积后续的条件
       safeDB := adultDB.Session(&gorm.Session{NewDB: true})
       
       // 这个查询只有 age > 18 和 city = 上海
       safeDB.Where("city = ?", "上海").Find(&shanghaiAdults)
       
       // 这个查询只有 age > 18 和 role = admin，不会被上面的上海污染
       safeDB.Where("role = ?", "admin").Find(&adminAdults)
       ```
    
  - **preload**
  
    1. **是什么**：Preload 的本质是 **两条（或多条）独立 SQL**，先查主表，再根据外键批量查关联表，最后在内存中组装。
  
    2. **怎么使用**：直接加上preload字段（***！注意：会加载出所有关联表的数据***，比如以下即使某用户没有金额>100的订单，该用户依然会被返回，只是 `Orders` 为空。）
  
       ```
       // 查所有用户，但每个用户只加载金额 > 100 的订单
       db.Preload("Orders", "amount > ?", 100).Find(&users)
       // SQL：
       // SELECT * FROM users;本质还是查询的用户                    ← 所有用户都返回
       // SELECT * FROM orders WHERE user_id IN (...) AND amount > 100;
       ```
  
  - **join**
  
    1. **是什么**：Joins 的本质是 **一条 JOIN SQL**，在数据库层面完成表连接。（*用于主表过滤*）
  
    2. 怎么使用：也是直接加上**joins**字段
  
       ```
       // 代码
       db.Joins("Orders").Find(&users)
       // 产生的 SQL（1 条）
       // SELECT users.* FROM users INNER JOIN orders ON orders.user_id = users.id;
       
       // ✅ 查"有未完成订单的用户"
       db.Joins("Orders", db.Model(&Order{}).Where("status = ?", "unpaid")).Find(&users)
       ```

### 非关系型数据库

#### redis：

1. **redis是什么**

   Redis是一个开源的高性能键值存储数据库，它提供了多种数据结构来存储数据，如字符串、哈希、列表、集合、有序集合等。Redis将数据存储在内存中，以提供快速的读写访问速度，并且能够通过异步的方式将数据持久化到磁盘上。它支持复制、Lua脚本、事务处理、不同级别的持久化选项以及多种客户端语言的接口。Redis广泛用于缓存、消息队列、短时数据存储和高性能的应用场景中。

2. **redis的特性**

   1. Redis支持数据的持久化，可以将内存中的数据保存在磁盘中，重启的时候可以再次加载进行使用。
   2.  Redis不仅仅支持简单的key-value类型的数据，同时还提供字符串（strings）、lists（列表）、sets（集合）和zsets（有序集合）、散列（hash）等数据结构的存储。

   3. Redis支持数据的备份，即master-slave模式的数据备份。

   4. 性能极高：Redis能读的速度是110000次/s,写的速度是81000次/s 。
   5. 原子性：Redis的所有操作都是原子性的，意思就是要么成功执行要么失败完全不执行。单个操作是原子性的。多个操作也支持事务，即原子性，通过MULTI和EXEC指令包起来。

   6. 丰富的特性：Redis还支持 publish(发布)/subscribe（订阅）, 通知, key 过期等等特性。

3. **redis的线程模型**：

   redis是单线程，但是其仍能抗住高并发，不仅是因为*数据储存在内存*里，还因为*其io多路复用*，一个线程能监听多个socket，一个线程高效处理大量并发连接，并且得益于单线程，*可以避免其切换线程时的性能开销*，还没有*锁竞争*。

5. **redis缓存问题**

   1.  缓存穿透

   - **现象**：大量请求查询**数据库和缓存中都不存在**的数据，请求全部打到数据库。
   - 解决
     - **缓存空值**：查不到的数据在缓存存个 null，设置短过期时间。
     - **布隆过滤器**：在缓存前加一层布隆过滤器，不存在的数据直接拦截。

   2.  缓存击穿

   - **现象**：某个**热点 Key** 在过期的瞬间，同时有海量请求打过来，缓存未命中，全部冲向数据库。
   - 解决
     - **互斥锁**：只允许一个线程查数据库并重建缓存，其他线程等待。
     - **逻辑过期**：物理上不设置过期时间，Value 中存逻辑过期时间。发现逻辑过期时，返回旧数据，异步线程更新缓存。
     - singleflight：相同 Key 的并发请求，只让第一个请求去执行，其他请求直接共享第一个请求的结果。

   3. 缓存雪崩

   - **现象**：大量 Key **在同一时间集中过期**，或者 **Redis 宕机**，导致海量请求打到数据库。
   - 解决
     - 过期时间加随机值，打散过期时间。
     - 搭建高可用集群（防宕机）。
     - 服务降级、限流、多级缓存（如加本地缓存 Guava/Caffeine）。

6. **缓存策略**：

   1. Cache-Aside（旁路缓存）：

      - 读：先查缓存，命中直接返回；未命中查 DB，再写回缓存。
      - 写：先更新 DB，再**删除**缓存（而不是更新缓存）

   2. 延迟双删：

      第一次删缓存后，可能有一个读请求在 DB 更新前读到了旧值并回写缓存，第二次删除把这个“脏缓存”清掉

      **流程**：

      1. 更新 DB。
      2. 删除缓存（第一次）。
      3. 延迟一段时间（通常 100–500ms，视并发和主从延迟而定）toutiao.com+1。
      4. 再次删除缓存（第二次）。

   3. **Canal + Binlog **：

      业务代码只写 DB，完全不碰缓存；由中间件监听 MySQL binlog，异步更新/删除缓存

      **流程**

      1. 业务服务 UPDATE MySQL
      2. MySQL 写 ROW Binlog
      3. Canal Server 模拟 Slave 拉取 Binlog
      4. Canal 解析出: users 表, id=123, UPDATE
      5. Canal Client 拉取（tcp直连）或 MQ 推送
      6. 解析表名 主键 操作类型
      7. 构造 Redis Key
      8. 删除或更新 Redis

## 关于微服务

### 微服务介绍

#### **1. 什么是微服务**

在介绍微服务时，首先得先理解什么是微服务，顾名思义，微服务得从两个方面去理解，什么是"微"、什么是"服务"， 微 狭义来讲就是体积小、著名的"2 pizza 团队"很好的诠释了这一解释（2 pizza 团队最早是亚马逊 CEO Bezos提出来的，意思是说单个服务的设计，所有参与人从设计、开发、测试、运维所有人加起来 只需要2个披萨就够了 ）。 而所谓服务，一定要区别于系统，服务一个或者一组相对较小且独立的功能单元，是用户可以感知最小功能集。

#### **2. 微服务由来**

微服务最早由Martin Fowler与James Lewis于2014年共同提出，[微服务架构](https://cloud.tencent.com/developer/techpedia/1527?from_column=20065&from=20065)风格是一种使用一套小服务来开发单个应用的方式途径，每个服务运行在自己的进程中，并使用轻量级机制通信，通常是HTTP API，这些服务基于业务能力构建，并能够通过自动化部署机制来独立部署，这些服务使用不同的编程语言实现，以及不同数据存储技术，并保持最低限度的集中式管理。

#### **3. 为什么需要微服务？**

在传统的IT行业软件大多都是各种独立系统的堆砌，这些系统的问题总结来说就是扩展性差，可靠性不高，维护成本高。到后面引入了SOA服务化，但是，由于 SOA 早期均使用了总线模式，这种总线模式是与某种技术栈强绑定的，比如：J2EE。这导致很多企业的遗留系统很难对接，切换时间太长，成本太高，新系统稳定性的收敛也需要一些时间。最终 SOA 看起来很美，但却成为了企业级奢侈品，中小公司都望而生畏。

- 服务治理：

  1. **服务发现**

     **Server 端（注册服务）**：

     ```
     package main
     
     import (
     	"log"
     	"kitex-demo/kitex_gen/api/echoservice"
     	"github.com/kitex-contrib/registry-etcd"
     )
     
     func main() {
     	// 1. 初始化 Etcd Registry
     	r, err := etcd.NewEtcdRegistry([]string{"127.0.0.1:2379"})
     	if err != nil {
     		log.Fatal(err)
     	}
     
     	// 2. 创建 Server，注入 Registry
     	svr := echoservice.NewServer(new(EchoServiceImpl),
     		server.WithRegistry(r), // 把自己注册到 Etcd
     		server.WithServiceAddr(&net.TCPAddr{Port: 8888}), // 显式指定注册的端口
     	)
     
     	err = svr.Run()
     	if err != nil {
     		log.Fatal(err)
     	}
     }
     ```

     **Client 端（发现服务）**：

     ```
     package main
     
     import (
     	"context"
     	"log"
     	"kitex-demo/kitex_gen/api"
     	"kitex-demo/kitex_gen/api/echoservice"
     	"github.com/kitex-contrib/registry-etcd"
     	"github.com/cloudwego/kitex/client"
     )
     
     func main() {
     	// 1. 初始化 Etcd Resolver
     	r, err := etcd.NewEtcdResolver([]string{"127.0.0.1:2379"})
     	if err != nil {
     		log.Fatal(err)
     	}
     
     	// 2. 创建 Client，注入 Resolver，去掉 WithHostPorts
     	c, err := echoservice.NewClient("echo-server", client.WithResolver(r))
     	if err != nil {
     		log.Fatal(err)
     	}
     
     	resp, err := c.Echo(context.Background(), &api.Request{Message: "Hello via Etcd"})
     	if err != nil {
     		log.Fatal(err)
     	}
     	log.Println(resp.Message)
     }
     ```

  2. **超时**

     超时是微服务防止级联雪崩的最基本手段。Kitex 区分**客户端超时**和**单次请求超时**。

     ```
     package main
     
     import (
     	"context"
     	"time"
     	"kitex-demo/kitex_gen/api"
     	"kitex-demo/kitex_gen/api/echoservice"
     	"github.com/cloudwego/kitex/client"
     	"github.com/cloudwego/kitex/client/callopt"
     )
     
     func main() {
     	// 1. 初始化客户端时，设置全局默认 RPC 超时时间 (3秒)
     	c, err := echoservice.NewClient("echo-server", 
     		client.WithHostPorts("127.0.0.1:8888"),
     		client.WithRPCTimeout(3 * time.Second), // 全局超时
     	)
     	if err != nil {
     		log.Fatal(err)
     	}
     
     	// 2. 针对某一次特定调用，覆盖全局超时时间 (5秒)
     	// 适用场景：某个导出接口天然耗时较长
     	resp, err := c.Echo(
     		context.Background(), 
     		&api.Request{Message: "Slow request"},
     		callopt.WithRPCTimeout(5 * time.Second), // 单次调用超时
     	)
     	
     	// ... 处理 resp
     }
     ```

  3. **熔断**

     当某个下游服务错误率飙升或响应极慢时，熔断器会“切断”调用，快速失败，防止拖垮当前服务。

     Kitex 内置了熔断器，通过 `circuitbreak.NewCBSuite` 注入，**默认不开启，需显式注入**。

     ```
     package main
     
     import (
     	"context"
     	"log"
     	"kitex-demo/kitex_gen/api"
     	"kitex-demo/kitex_gen/api/echoservice"
     	"github.com/cloudwego/kitex/client"
     	"github.com/cloudwego/kitex/pkg/circuitbreak"
     )
     
     func main() {
     	// 1. 初始化 CBSuite
     	// 默认策略：如果错误率超过 50%，或者连续 5 个慢调用，触发熔断
     	cbSuite := circuitbreak.NewCBSuite(
     		circuitbreak.WithErrorRate(0.5),    // 错误率阈值
     		circuitbreak.WithSlowCallRate(0.5), // 慢调用率阈值
     	)
     
     	// 2. 注入到 Client
     	c, err := echoservice.NewClient("echo-server",
     		client.WithHostPorts("127.0.0.1:8888"),
     		client.WithCircuitBreaker(cbSuite), // 开启熔断
     	)
     	if err != nil {
     		log.Fatal(err)
     	}
     
     	resp, err := c.Echo(context.Background(), &api.Request{Message: "Test CB"})
     	if err != nil {
     		// 当触发熔断时，返回的错误会是 *circuitbreak.ErrCircuitOpen
     		log.Printf("Call failed: %v\n", err)
     		return
     	}
     	log.Println(resp.Message)
     }
     ```

  4. **限流**

     限流分为**服务端限流**（保护自己不被打挂）和**客户端限流**（限制对下游的并发），通常在服务端配置更多。

     Kitex 内置了连接数和 QPS 限流器，通过 `server.WithLimit` 注入。

     **Server 端开启限流**：

     ```
     package main
     
     import (
     	"log"
     	"kitex-demo/kitex_gen/api/echoservice"
     	"github.com/cloudwego/kitex/server"
     	"github.com/cloudwego/kitex/pkg/limit"
     )
     
     func main() {
     	// 1. 配置限流参数
     	limitOpt := &limit.Option{
     		MaxConnections: 1000, // 最大并发连接数
     		MaxQPS:         500,  // 每秒最大请求数 (令牌桶算法)
     	}
     
     	// 2. 创建 Server 并注入
     	svr := echoservice.NewServer(new(EchoServiceImpl),
     		server.WithLimit(limitOpt), // 开启限流
     	)
     
     	err := svr.Run()
     	if err != nil {
     		log.Fatal(err)
     	}
     }
     
     ```
  
     **注意**：Kitex 默认的 QPS 限流对标准 `gRPC` 协议**不生效**，仅对 Thrift/Kitex Protobuf 生效。如果你的服务使用 gRPC 协议，需要通过 `WithGRPCInitialWindowSize` 等流控参数来限制，或自己编写中间件限流。
  
  5. **重试**
  
     重试是解决偶发性网络抖动或下游临时不可用的有效手段，但**重试是一把双刃剑**：如果下游已经过载，重试反而会引发雪崩。因此，Kitex 的重试策略允许你精细控制“什么时候重试”、“重试几次”以及“怎么退避”。
  
     **核心配置**：
  
     - `retry.NewRetryPolicy()`：创建重试策略。
     - `retry.WithMaxRetryTimes()`：最大重试次数（不包含首次调用）。
     - `retry.WithRetryCondition()`：重试条件（比如只在遇到网络错误或超时时重试）。
     - `retry.WithBackoff()`：退避策略（如固定退避、随机退避，防止重试风暴）。
  
     **示例代码（客户端开启重试）**：
  
     ```
     package main
     
     import (
     	"context"
     	"log"
     	"time"
     
     	"kitex-demo/kitex_gen/api"
     	"kitex-demo/kitex_gen/api/echoservice"
     	"github.com/cloudwego/kitex/client"
     	"github.com/cloudwego/kitex/pkg/retry"
     )
     
     func main() {
     	// 1. 定义重试策略
     	retryPolicy := retry.NewRetryPolicy(
     		retry.WithMaxRetryTimes(2), // 最多重试 2 次
     		retry.WithRetryCondition(retry.ShouldRetry), // 默认条件：网络错误或超时才重试
     		retry.WithBackoff(retry.NewExponentialBackoff(
     			100*time.Millisecond, // 最小退避时间
     			1*time.Second,        // 最大退避时间
     		)),
     	)
     
     	// 2. 注入到 Client
     	c, err := echoservice.NewClient("echo-server",
     		client.WithHostPorts("127.0.0.1:8888"),
     		client.WithRetryPolicy(retryPolicy), // 开启重试
     		client.WithRPCTimeout(3*time.Second), // 务必设置超时，重试是基于超时触发的
     	)
     	if err != nil {
     		log.Fatal(err)
     	}
     
     	resp, err := c.Echo(context.Background(), &api.Request{Message: "Test Retry"})
     	if err != nil {
     		log.Printf("Call failed after retries: %v\n", err)
     		return
     	}
     	log.Println(resp.Message)
     }
     ```
  
     > ⚠️ **重试的避坑指南（极其重要）**：
     >
     > 1. **仅对幂等接口重试**：如果是写操作（如扣款、下单），除非下游做了严格的幂等性保障，否则**严禁开启重试**，否则会导致数据重复写入！
     > 2. **重试必须配合熔断**：如果下游彻底挂了，重试只会白白消耗线程。必须配置熔断器，当下游错误率飙升时，熔断器打开，直接快速失败，不再发起重试。
     > 3. **注意超时时间**：确保 `RPCTimeout > 单次请求超时 * (MaxRetryTimes + 1)`，否则根本没有时间留给重试。
  
  6. **降级**
  
     降级是指当下游服务不可用或响应过慢时，**不再调用下游，而是直接返回一个预设的兜底结果**，保证核心链路不阻塞。
  
     在 Kitex 中，降级通常和**熔断**配合使用。当熔断器处于 Open 状态时，请求会被拦截，此时就可以触发降级逻辑。Kitex 在 `circuitbreak` 模块中提供了 `WithFallback` 选项来注入降级函数。
  
     **核心配置**：
  
     - `circuitbreak.WithFallback()`：指定降级回调函数。当熔断触发或发生特定错误时，执行该函数返回兜底数据。
  
     **示例代码（客户端开启熔断+降级）**：
  
     ```
     package main
     
     import (
     	"context"
     	"log"
     
     	"kitex-demo/kitex_gen/api"
     	"kitex-demo/kitex_gen/api/echoservice"
     	"github.com/cloudwego/kitex/client"
     	"github.com/cloudwego/kitex/pkg/circuitbreak"
     )
     
     func main() {
     	// 1. 定义降级函数
     	fallbackFunc := func(ctx context.Context, req interface{}, err error) (interface{}, error) {
     		// 这里可以根据 err 判断是什么错误，决定是否降级
     		// 例如：如果是熔断错误，返回默认的兜底响应
     		log.Printf("[Degradation] Triggered fallback due to: %v", err)
     		
     		// 返回兜底数据（注意类型必须与正常返回值一致）
     		return &api.Response{Message: "Degraded: Default response from cache"}, nil
     	}
     
     	// 2. 创建带降级的熔断器 Suite
     	cbSuite := circuitbreak.NewCBSuite(
     		circuitbreak.WithErrorRate(0.3), // 错误率超过 30% 触发熔断
     		circuitbreak.WithFallback(fallbackFunc), // 注入降级函数
     	)
     
     	// 3. 注入到 Client
     	c, err := echoservice.NewClient("echo-server",
     		client.WithHostPorts("127.0.0.1:8888"),
     		client.WithCircuitBreaker(cbSuite),
     	)
     	if err != nil {
     		log.Fatal(err)
     	}
     
     	// 模拟调用：当下游挂掉触发熔断时，会自动走到 fallback
     	resp, err := c.Echo(context.Background(), &api.Request{Message: "Test Degradation"})
     	if err != nil {
     		// 如果 fallback 返回了 error，这里才会收到 err
     		log.Fatal(err)
     	}
     	
     	// 此时如果下游不可用，这里打印的将是兜底信息：
     	// "Degraded: Default response from cache"
     	log.Println(resp.Message)
     }
     ```
  
     > 💡 **降级的进阶玩法**：
     > Kitex 的 `WithFallback` 不仅在熔断开启时触发，你也可以通过自定义 `circuitbreak.ShouldFallback` 函数来决定**什么错误才降级**。例如：只有下游返回 `DB Error` 时才降级返回缓存，如果是 `Param Error` 则直接抛出给调用方。

## 消息队列

***关于消息队列，个人感觉就像是go里的channel，只不过一个是存在于go进程的内存里，一个是存在网络上连接不同的服务器***

#### kafka

- **是什么**：

  kafka是一个分布式数据流平台，使应用程序能够实时发布、订阅、存储和处理消息流。发布/订阅 （pub/sub） 系统的特点是发送方将消息推送到一个中心点进行分类。

- **有哪些组件**

  1. **Broker（代理）**：Kafka集群中的一台服务器。
  2. **Topic（主题）**：消息的逻辑分类。
  3. **Partition（分区）**：**Kafka高并发的核心**。一个Topic可以分为多个Partition，分布在不同的Broker上。Partition内部是有序的，但全局（跨Partition）无序。
  4. **Offset（偏移量）**：消息在Partition中的唯一ID（单调递增的long型数字）。
  5. **Producer（生产者）**：发送消息的应用。
  6. **Consumer（消费者）**：接收消息的应用。
  7. **Consumer Group（消费者组）**：**Kafka实现单播/广播的核心**。一条消息只能被同一个组内的一个消费者消费（单播），但可以被不同的组同时消费（广播）。

- **有关于组件**

  - 什么是消息？

  消息或记录是包含应用程序数据的键/值对。每条消息都存储在一个topic中。此消息在其配置的生命周期内是持久的。主题中每条消息的位置是其偏移量 。消息通常按照添加顺序从每个分区中使用。

  - 什么是topic？

  同一类消息的集合，topic通常在1个或者多个的broker跨区复制实现容错，每个topic上有不同的分区。

  ![img](https://developer.qcloudimg.com/http-save/yehe-10204959/04eba580fd497345d8b4924b3a22a71f.png)

  - 什么是分区？

  分区是包含写入消息的topic的子集。新消息会进入到分区末尾，可以确保消息的有序性，多个分区可以在负载较高，数据共享复制的情况下提高性能。

  另外分区可以在不同的broker之间进行复制，其中一个broker作为leader，用于消息的接收及消费，当该broker异常时，其中一个副本重新选举为leader。

  ![img](https://developer.qcloudimg.com/http-save/yehe-10204959/87f68071a4c8409e1a8deb1d0d8b9d20.png)

  - 什么是生产者?

  创建者将消息发布到主题，该主题将每条消息附加到分区的末尾。默认情况下，如果消息包含键，则使用键的哈希值来决定哪个分区接收消息。如果 key 为 null，则循环算法将平衡所有分区之间的消息存储。

  Kafka 保证，只要不添加新的分区，当使用默认分区器时，具有相同键的元素就会存储在同一个分区中。

  - 什么是消费者？
  
  发布到主题的每条消息都会传送给已订阅该主题的使用者。使用者可以从 topic 分区中的任何偏移量读取数据。在大多数情况下，使用者会线性推进其偏移量，但它可以从任何偏移量开始，并以任何顺序读取消息。使用者通常会将其偏移量“提交”回Kafka集群，以便使用者可以从中断的地方继续，例如，在重新启动时。

- **使用示例**

  - 生产者示例

    `kafka-go` 封装了 `kafka.Writer` 来发送消息，它自带连接池和重试机制，使用起来非常简单。

    ```
    package main
    
    import (
    	"context"
    	"fmt"
    	"log"
    	"os"
    	"os/signal"
    	"syscall"
    	"time"
    
    	"github.com/segmentio/kafka-go"
    )
    
    const (
    	Topic    = "order-events"
    	Broker   = "localhost:9092"
    )
    
    func main() {
    	// 1. 初始化 Writer
    	w := &kafka.Writer{
    		Addr:         kafka.TCP(Broker),
    		Topic:        Topic,
    		// 相当于我们之前讲的 acks=all，保证消息不丢
    		RequiredAcks: kafka.RequireAll, 
    		// 批量发送的配置，提升吞吐量
    		BatchTimeout: 10 * time.Millisecond,
    		BatchSize:    100,
    	}
    	defer w.Close()
    
    	// 2. 监听系统信号，实现优雅退出
    	sigchan := make(chan os.Signal, 1)
    	signal.Notify(sigchan, syscall.SIGINT, syscall.SIGTERM)
    
    	// 3. 模拟持续发送消息
    	go func() {
    		for i := 0; ; i++ {
    			// 构建消息
    			// Key: 保证同一个订单ID的路到同一个Partition，保证局部有序
    			// Value: 消息体
    			msg := kafka.Message{
    				Key:   []byte(fmt.Sprintf("OrderID-%d", i%10)), 
    				Value: []byte(fmt.Sprintf("订单 %d 创建成功", i)),
    				// 也可以带上 Header，类似 HTTP Header，常用于链路追踪
    				Headers: []kafka.Header{
    					{Key: "trace-id", Value: []byte("trace-123-abc")},
    				},
    			}
    
    			// 使用 WriteMessages 发送
    			err := w.WriteMessages(context.Background(), msg)
    			if err != nil {
    				log.Printf("Failed to write message: %v\n", err)
    			} else {
    				log.Printf("Produced: Key=%s, Value=%s\n", msg.Key, msg.Value)
    			}
    
    			time.Sleep(1 * time.Second) // 模拟业务耗时
    		}
    	}()
    
    	log.Println("Producer is running... Press Ctrl+C to stop.")
    	<-sigchan
    	log.Println("Shutting down producer...")
    }
    ```

  - 消费者示例

    `kafka-go` 使用 `kafka.Reader` 来消费消息。默认情况下 `Reader` 会自动提交 Offset，但在生产环境中，为了保证消息不丢失，我们**必须关闭自动提交**，在业务逻辑处理成功后手动提交。

    ```
    package main
    
    import (
    	"context"
    	"fmt"
    	"log"
    	"os"
    	"os/signal"
    	"syscall"
    
    	"github.com/segmentio/kafka-go"
    )
    
    const (
    	Topic    = "order-events"
    	Broker   = "localhost:9092"
    	GroupID  = "order-service-group" // 消费者组ID
    )
    
    func main() {
    	// 1. 初始化 Reader
    	r := kafka.NewReader(kafka.ReaderConfig{
    		Brokers:  []string{Broker},
    		GroupID:  GroupID,
    		Topic:    Topic,
    		MinBytes: 10e3, // 10KB
    		MaxBytes: 10e6, // 10MB
    		// ★★★ 核心配置：关闭自动提交 ★★★
    		CommitInterval: 0, // 设置为 0 表示关闭自动提交
    	})
    	defer r.Close()
    
    	// 2. 监听系统信号
    	sigchan := make(chan os.Signal, 1)
    	signal.Notify(sigchan, syscall.SIGINT, syscall.SIGTERM)
    
    	// 3. 消费循环
    	go func() {
    		for {
    			// FetchMessage 只拉取消息，不自动提交 Offset
    			// 它会阻塞等待直到有新消息
    			m, err := r.FetchMessage(context.Background())
    			if err != nil {
    				if err == context.Canceled {
    					break // 上下文取消，退出循环
    				}
    				log.Printf("Failed to fetch message: %v\n", err)
    				continue
    			}
    
    			log.Printf("Consumed: Partition=%d, Offset=%d, Key=%s, Value=%s\n",
    				m.Partition, m.Offset, string(m.Key), string(m.Value))
    
    			// TODO: 这里执行你的业务逻辑，比如写入数据库
    			// 如果业务逻辑报错，不要调用 CommitMessages，下次启动还会再消费这条
    			err = processBusinessLogic(m)
    			if err != nil {
    				log.Printf("Business logic failed for offset %d: %v\n", m.Offset, err)
    				continue // 处理失败，不提交，等待下次消费
    			}
    
    			// ★★★ 业务处理成功，手动提交 Offset ★★★
    			// 提交的是 FetchMessage 拿到的 m 的 Offset
    			if err := r.CommitMessages(context.Background(), m); err != nil {
    				log.Printf("Failed to commit messages: %v\n", err)
    			}
    		}
    	}()
    
    	log.Println("Consumer is running... Press Ctrl+C to stop.")
    	<-sigchan
    	log.Println("Shutting down consumer...")
    }
    
    // 模拟业务逻辑
    func processBusinessLogic(m kafka.Message) error {
    	// 模拟偶尔失败
    	// if rand.Intn(10) == 0 { return fmt.Errorf("random error") }
    	return nil
    }
    ```

## 关于AI Agernt

- **是什么**

  AI Agent（Artificial Intelligence Agent，人工智能代理）是一种能够**自主感知环境、进行决策并执行任务**的智能实体。其核心特征在于将大语言模型（LLM）作为“大脑”，结合规划、记忆、工具调用等能力，实现复杂任务的自动化处理。例如，用户只需输入“取消订阅服务”，AI Agent即可自主分解步骤、调用支付接口完成操作。

（agent大概就是给llm使用prompt加上循环和tool）

- **tool**：

  Tool 本质上是“带参数 schema 的可调用能力”。 在 Go 里它可以由普通函数实现，框架会把它包装成 LLM 可理解的工具描述（如名称、参数、JSON schema）。 LLM 不执行代码，只负责生成“调用哪个工具、传什么参数”。有了tool才能让llm具有agent的功能去进行工作。

- **ai agent模式和workflow模式**

  **1. Workflow：被设定好的自动化流程**

  直白来讲，Workflow 是一套**人为定义、刚性执行**的自动化流程。使用者需要提前梳理完整的执行链路，明确每一个操作节点、执行顺序、触发条件。它更像一份固定的操作说明书，系统只会严格按照预设步骤完成任务，不存在主观判断能力。

  Workflow 的核心是流程自动化，全程依赖人工干预完成前置操作：从流程规划、规则设定，到任务启动、流程终止，全部由人把控。即便接入大模型增强能力，它也仅能完成简单的数据校对、文字优化等辅助工作，无法自主更改流程逻辑，更不能主动应对突发问题。

  **2. AI Agent：具备思考能力的执行主体**

  不同于死板的工作流，AI Agent 是拥有独立感知、思考、决策能力的智能执行体。它可以把用户的模糊目标拆解为多项细分任务，自主判断最优执行路径，还能在多种解决方案中，结合实际场景筛选适配方案。

  AI Agent 能够形成闭环运行逻辑：自主规划任务、调用工具执行、观测反馈数据、做出优化决策。在任务执行过程中，一旦识别到数据异常、流程卡顿等问题，它可以自主复盘修正，无需人工介入调整，这也是智能体区别于传统工作流的最大亮点。

  3. **Agentic Workflow**

     尽管agent看上去更加便捷也更加灵活，但是由于目前行业内并没有成熟的通用型 AI Agent，高阶自主智能体仍处于技术研发打磨阶段。所以市面上绝大多数商用智能体产品，并非原生智能架构，而是**基于 Workflow 封装改造的轻量化框架**。（概括一下就是：**整体用 Workflow 骨架**：主流程、关键分支是确定性的，保证可控和可审计。**局部用 Agent**：在意图识别、知识检索、异常判断等“需要脑补”的节点，让 LLM 自主决策）

- **react**

  不是一次性想完后再调用工具返回结果，而是根据工具返回的消息进行思考后返回

  ```
  think（LLM 决定下一步）
    → act（调工具）
    → observe（看结果）
    → think（继续推理）
    → ...
    → 最终回答（LLM 决定不再调工具）
  ```

  适合需要多步推理的任务，比如"先查用户信息，再根据信息查课程，再生成推荐"。

- **rag和memory**

  - **rag**：

    - rag的作用：

      大语言模型（LLM）存在三大固有缺陷，RAG 正是为了解决这三点而生：

      1. **幻觉**：一本正经地胡说八道，生成不可靠的内容。
      2. **知识滞后**：训练数据有截止日期，不知道最新发生的事。
      3. **私有数据缺失**：不知道企业内部的专有知识（如内部文档、用户数据）。

      **RAG 的本质**：给大模型外挂一个“开卷考试的知识库”，让它在生成回答前，先去检索相关的真实资料，基于检索到的资料（Context）来回答，从而提升回答的准确性和可信度。

      **核心公式**：`RAG = 检索 + 上下文注入 + LLM 生成`

    - 基础架构：

      最基础的 RAG 是线性的三个阶段：**索引 → 检索 → 生成**

      **索引**就是将上传的文档进行解析分块向量化存入向量数据库里
      
      **检索**就是将用户的问题向量化去向量数据库找相似的数据
      
      **生成**是将检索出来的相似的知识扔给llm回答
      
      
      
      但是普通的rag又存在非常明显的缺陷和天花板：
      
      1. 检索：向量检索的本质是计算文本在嵌入空间中的距离，这就会导致：
      
         1.普通rag的对于用户的模糊提问无法做出正确的响应（比如无法识别用户询问上一个问题是什么）；
      
         2.可能会出现语义相似但毫无逻辑的情况（如询问老刘喜欢吃什么，可能检索出老刘喜欢女人）；
      
         3.会出现多跳推理缺失（比如询问老刘的是谁，住哪里？如果知识库的两个文本块是老刘是邻居，住翻斗花园，因为第二块文本无字面意义上的相似，所以无法检索到）
      
      2. 索引：文本是需要切分去向量化的，那么就会出现上下文割裂的情况（老刘昨天吃了水果，吃的苹果，就有可能被切成两段，向量检索就无法检索到老刘昨天吃苹果）
      
      3. 生成：并非将所有内容一股脑扔给llm就能准确生成回复了，llm可能也会出现
      
         1.**中间信息丢失**：大模型对长上下文的注意力呈U型分布——对开头和结尾的信息关注度高，对中间部分的信息极易忽略；
      
         2.**信息冲突与幻觉**：**外部冲突**：检索到的多个文档块之间可能存在信息过时或自相矛盾，大模型往往无法辨别真伪，可能随意选取一个，甚至把两者揉捏在一起产生幻觉。**内外冲突**：检索到的外部知识与大模型内部的预训练知识冲突时，大模型有时会“固执己见”，忽略检索内容，依然用自己的旧知识回答。
      
         3.**冗余信息干扰**：为了保证召回率，普通RAG可能会塞入大量相关但无用的背景信息，这不仅浪费了Token，还可能误导大模型，导致回答偏离重点。
      
      4. 缺少全局观：无法对知识库里的数据进行总结，只能检索局部内容
      
    - rag的升级
    
      1. **检索**：
    
         1.用户提问模糊，可以先让llm先将用户的口语化提问转成规范的搜索词，如果问题过短可以使用**HyDE（假设性文档嵌入）**，先让llm猜一个长答案去向量库里检索答案，因为长答案的语义更丰富，反而更容易检索到真正的相关文档。
    
         2.语义相似但无逻辑，使用混合检索，将向量检索和关键词检索结合起来并使用[ffr算法](https://docs.azure.cn/zh-cn/search/hybrid-search-ranking)进行打分排序，关键词检索可使用[bm25算法](https://cloud.tencent.com/developer/article/2661977)
    
         3.出现多跳推理缺失，使用react agent0，让ai可以进行多次查询，引入[GraphRAG](https://cloud.tencent.cn/developer/article/2462755?policyId=20240000&traceId=),通过**图结构**和**语义关系**，将分散的知识链接成网，让计算机不仅能存储信息，还能像人一样进行联想、推理和解释。
    
      2. **索引**：选择合理的[分块策略](https://developer.jdcloud.com/article/4408),没有万能的分块策略
      
      3. **生成**：直接生成后返回结果值可能会因为调用的大模型产生幻觉而导致回复质量较低，所以需要检查llm返回的回答质量，可以调用[RAGAS 框架](https://docs.ragas.io/en/latest/getstarted/quickstart/)进行回复评估
      
      4. **全局观**：依旧使用GraphRAG通过“图 + 社区摘要”，把碎片化知识组织成 **多粒度结构**，既保留细节，又能看全局。
    
  - **memory**：
  
    - 是什么：
  
      用于记忆用户所说的话，单次调用llm是不会带有用户的上一个问题的，那么我们想要让ai有记忆，就要将以前的问题内容注入到prompt中。
  
    - 记忆层的设计思路：
  
      现在主流的agent记忆层的设计是：
  
      1. 三维漏斗筛选（持久化，结构化，个性化）
         - **持久化筛选（要不要存？）**：对应我说的 **“重要性打分”** 和 **“阈值过滤”**。不是所有消息都有资格进入长期记忆，只有 score > 阈值的才掉进漏斗底层。同时配合“防抖”，防止同一话题短时间内重复写入。
         - **结构化筛选（存成什么样子？）**：对应我说的 **“内容变换：提取/重构/打标签”**。把口语化的“@bot 以后用 make deploy”，重构为结构化的 `{"type": "rule", "action": "deploy", "cmd": "make deploy", "forbidden": "go run"}`，附带时间、群号等元数据。
         - **个性化筛选（跟谁有关？）**：对应我说的 **“用户/群组画像/偏好”** 和 **“归因”**。把记忆绑定到具体实体上（例如：提取出“张三是 Gopher 偏好 Cobra”，而不是仅仅存一句“我喜欢 cobra”）。
  
      2. graphrag架构：
  
         使用图数据库将记忆元素关联起来
  
      3. 动态反思机制
         - **微观反思（写入时）**：我说的“把对话重写为陈述/规则”，本质上是让 LLM 在写入前做了一次小反思（“这段聊天到底得出了什么结论？”）。
         - **宏观反思（后台定时）**：对应我说的“定期扫描：长期未被召回+低分淘汰”、“与最新群规冲突的记忆自动标注”。
  
      4. 冷热分级存储
  
         热库：通常用内存数据库（redis等）存储最近的对话记录，服务于精确、高频、时序相关的记忆
  
         温库（可以和热库合并）：用向量数据库检索语义
  
         冷库：用于存储时间过久的记忆（可用列数据库），主要服务于宏观分析和统计
